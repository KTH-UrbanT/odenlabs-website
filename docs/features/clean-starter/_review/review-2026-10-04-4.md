## Findings and verdicts

### R4-01 [stage-1/2, medium] Raw `<` or `</svg>` in an attribute hides a tag's `url()`: **Fix now** (T29)

`src/lib/offsite-requests.ts:113` (tag pattern `"[^"<]*"|'[^'<]*'`), `:64`
(`<(\/?)(svg|style)\b[^<>]*>`), `:115` (an attribute name must follow whitespace), and the comment at
`:109-110`. This touches the spec §6 NFR. Both reviewers found it independently.

The comment assumes that built attribute values carry `<` as `&lt;`. That assumption is wrong in two
places:

- In a scratch build, Astro 7 keeps `<` and `</svg>` raw in expression attributes (`title={"1<2"}` →
  `title="1<2"`). Only static attributes get `&lt;`.
- Markdown raw HTML also passes through raw. hast-util-to-html escapes only `"` and `&` in
  double-quoted values.

The guard returns `[]` for these inputs:

- **Real Astro output:**
  `<div class="card" title="Jane <PI>" style="background-image:url(&quot;https://cdn.example.com/jane.jpg&quot;)"></div>`.
  The T24 code at `cc88c9b` reported this one, so it is a regression.
- **`</svg>` inside an attribute:** `<svg aria-label="a</svg>b"><style>…url(&quot;https://o.example.com/…&quot;)…</style></svg>`.
  The SVG depth reaches 0 early.
- **`<` inside an SVG attribute:** `<svg aria-label="a<b"><style>…</style></svg>`. The pattern at `:64`
  does not match the opening tag.
- **`/` as a separator:** `<svg><path/mask="url(&quot;https://m.example.com/m#m&quot;)"/></svg>`.

### R4-02 [stage-1/2, low] Legacy named references without `;` are not decoded: **Fix now** (T29)

`src/lib/offsite-requests.ts:40`. This touches the spec §6 NFR.

Browsers decode `&quot`, `&amp`, `&lt` and `&gt` without `;`:

- in an attribute value, when the next character is not `=` and not alphanumeric;
- always, inside an SVG `<style>`.

These inputs return `[]`, but the browser fetches them:

- `<div style="background:url(&quot https://a.example.com/x&quot)">`
- `url(&quot//lq.example.com/x&quot)`
- `<svg><style>.a{fill:url(&quothttps://b.example.com/p#p&quot)}</style></svg>`

Astro never emits this form. It only arises from hand-written markup or Markdown raw HTML.

### R4-03 [stage-2, low] Named entities are matched without regard to case: **Fix now** (T29)

`src/lib/offsite-requests.ts:46` (`NAMED[name!.toLowerCase()]`).

Browsers treat entity names as case-sensitive: `&Colon;` is U+2237, and `&SOL;` does not exist. So
`url(&quot;https&Colon;//d.example.com/x&quot;)` is reported, even though the browser resolves it as a
same-site relative URL.

This is a false positive: the build fails, but no visitor is affected (CLAUDE.md). It is fixed along
with R4-02 because the same table changes.

### R4-05 [stage-1/2, low] ux-flows US-06 check order disagrees with the planner: **Fix now** (T30)

`ux-flows.md:150-160, 173-177` against `deploy/plan.ts:369-437`. This touches AC-11b, AC-12 and
AC-13b.

The two disagree in three ways:

- **Order:** ux-flows says "five checks run in order" and puts the record/folder check first. The code
  runs `protected-clash` → `approved-in-build` → `layout-clash` before the record checks, and runs the
  record checks only when deletion is on.
- **Missing check:** `approved-in-build` is not in the list.
- **Failure scenario:** with deletion on, a wrong folder holding a stray `_astro` file stops with
  `layout-clash`, but ux-flows predicts `no-previous-record`.

T28 extended the sentence without fixing the order.

### R4-07 [stage-2, low, outside the diff] `url()` scan is quadratic on malformed input: **Fix now** (T29)

`src/lib/offsite-requests.ts:121` (`/url\(\s*["']?([^"')]*?)["']?\s*\)/gi`), unchanged since T17.

When there is no closing `)`, each `url(` scans to the end of the input. `"url(".repeat(200000)` (0.8 MB)
took about 126 s. Astro never emits this, so the only cost is a hung build.

The third pass checked linearity only for the decoder, which this does not contradict.

### R4-08 [stage-1, low] `isOffSite` keeps an embedded tab or newline: **Defer** (joins R-09, spec §8)

`src/lib/offsite-requests.ts:11`. The URL parser strips tab and newline, so `src="ht<TAB>tps://x"`
fetches off-site, but the guard misses it. The cause is the same as R-09's `/\host` and `http:/host`
(scheme parsing that differs from the browser's). It is added to the existing R-09 entry, which stays
due 2026-10-31.
